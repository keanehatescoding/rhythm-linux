## 3. Testing
- [x] Unit tests pass (86 as of this commit)
- [x] Tests run in CI on every push: `.github/workflows/tests.yml` runs on GitHub and passes on `master` (run 42075149501, commit `126e8cb`). The first runs failed because the runner had no GStreamer libav decoders for AAC and ALAC; `gstreamer1.0-libav` is now installed in the workflow.
- [x] GUI tests: `tests/test_gui.py` covers the library list, search, the rating filter and export of shown tracks, using generated WAV files. It runs under `xvfb-run` and is skipped with no display. CI runs it under Xvfb (workflow not yet run on GitHub).
- [x] Large library: at least 5,000 tracks scanned, sorted, filtered and played without freezing the window. The track list is a virtualised `Gtk.ListView` over a `Gio.ListStore`, with a `Gtk.FilterListModel` for search. `tests/test_large_library.py` builds 5,000 WAV files and checks that every track is shown after the scan, that search narrows to one, that sort by album keeps all 5,000, and that playback starts; each UI pause must stay under 1 s (measured about 80 ms). Earlier benchmark: scan to 5,000 about 10 s on this machine, the same on the old list, so the earlier 3–6 s was from different conditions; search pause was about 380 ms before the change and 74–81 ms after.
- [~] **open** Formats: MP3, AAC/M4A, FLAC, WAV, ALAC, AIFF checked for tags, cover art and playback. Tags and cover art: `tests/test_formats.py` (MP3, AAC, ALAC, FLAC, AIFF with ID3 tags). Fixed: AIFF ID3 tags were not read because mutagen's easy mode skips them. Playback: all six formats (plus AIFF with ID3) play without error for 2 s in a manual check, and now in `tests/test_playback_formats.py` (each format plays through the real `Player` for 2 s with no error and the position advancing). Known limits: WAV and AIFF files with no ID3 tags show the filename; AIFF text chunks (NAME/AUTH) are not read.
- [x] Long session: a few hours of play, shuffle and repeat, with no growth in memory or errors in the log. Soak script (not in the repo) drives the real window through next, shuffle, repeat, pause, seek and play on 60 half-second WAV files. A 5-minute run: RSS 151.2 MB at 60 s, 151.7 MB at 300 s (+444 kB, slowing down: +72 kB in the last 75 s); longest UI pause 23 ms; no WARNING lines in the app log. GStreamer printed "Trying to dispose element inputselector…, but it is in PLAYING instead of the NULL state" once in that run (also once in a 15-minute run). That is a playbin internal, not an app log line. A 15-minute run was killed by timeout before reporting, so it is not a clean result. Where it comes from (gdb, GStreamer domain made fatal): the last reference to a playbin `inputselector` is dropped in `gst_bus_source_dispatch` on the main loop while the element is still PLAYING. Reproduction with `Player` alone did not trigger it (150 gapless and 150 crossfade changes, plus seek, pause and mid-stream play, about 1,000 changes in total). Decision: keep gapless playback as it is and accept the warning for now. Multi-hour run (12,172 s, 5 Nov 2026 21:22 to 6 Nov 00:45): about 16,000 random actions (next, previous, play/pause, seek, shuffle, repeat, stop) on 60 half-second WAVs in the real window under Xvfb. RSS stayed between 139.8 and 140.7 MB across 162 one-minute samples; longest UI pause 27 ms in the first sample and 3 ms or less after; the app log is empty (no WARNING or ERROR); no GStreamer dispose warning appeared in stderr. The script is in the scratchpad, not the repo. This run does not reproduce the earlier GStreamer warning, so it is still unexplained.

## 4. Reliability
- [x] Review the broad `except Exception` catches: `library.py` now catches mutagen's `MutagenError` for damaged or unsupported files (fall back to the filename, silently), `OSError` for unreadable files (logged as a warning), and `TypeError`/`ValueError`/`IndexError` for malformed cover data (logged). Checked by fuzzing 3,000 damaged files through `read_track` and `read_cover`: no exception escapes. The two in `ui.py` stay broad on purpose, at the worker-thread boundaries, where they must always report back (traceback logged). `iphone.py` has no broad catches.
- [x] Logging: warnings and errors go to `rhythm-linux.log` in the data folder (rotated at 1 MB, 3 kept) and to stderr; the app still starts if the folder cannot be written (`tests/test_logsetup.py`)
- [x] Crash test: the app was killed with SIGKILL during playback (10 runs) and during a scan (10 runs); settings, playlists and stats stayed valid JSON with no `.json.bak` and no leftover temp files. The harness is in the scratchpad, not the repo. Scan kills were not confirmed to land mid-scan.
- [x] Corrupt-data test: damaged `settings.json`, `playlists.json` and `stats.json` are moved to `.json.bak` and the app starts with defaults (`tests/test_corrupt_data.py`)

## 5. Phone features
- [x] Check at startup that `ifuse`, `ideviceinfo` and `kdeconnect-cli` exist; show a clear message in the UI when one is missing. `rhythm_linux/phone_tools.py` lists the missing tools per feature (`tests/test_phone_tools.py`). The notice is added to the status bar after the scan, and each phone action names the missing tool instead of failing (iPhone browsing never starts; KDE Connect sending no longer reports "No paired phone"). Checked in the running window with `kdeconnect-cli` hidden.
- [~] **open** Test on a second distribution and a second iPhone model. The iPhone connected now is an iPhone18,1 on iOS 27.2: `python3 -m rhythm_linux.iphone` finds it and lists 0 audio files. The read-only mount shows Photos and video (DCIM, PhotoData), Books and an empty `Music` folder; the music database sits in `iTunes_Control`, which the project does not read. So the browse and mount work, but there is nothing to play. No second distribution tested.
- [x] Play counts for iPhone files: keyed by device and file, not by mount path. `iphone.play_key` gives `iphone:<UDID>:<path on the phone>`; `Track.play_key` returns it, and every rating and play-count call uses it (`tests/test_iphone_play_counts.py`). Checked in the running window with a fake phone row: the play counted under the device key. Counts saved before this change, under mount paths, are left in stats.json and no longer used.
- [x] A phone that is unplugged or locked during browse shows an error, not a hang. Commands already had timeouts; a command that times out now shows "The phone did not answer…". A directory listing on a stale mount has no timeout, so the view gives up after 60 s (`PHONE_READ_TIMEOUT_S`), drops the late answer and tries to release the mount in the background. The read thread itself can stay blocked until the mount returns. Tested with simulated timeouts in `tests/test_gui.py`; not tested with a real phone or a real stuck mount.
- [x] Mount is always released on quit, including quit during a mount (checked). `release_phone` waits up to 20 s for an in-flight mount, then unmounts, and a failing unmount is logged, not raised. Ordering and failure cases are tested with stubbed mount calls in `tests/test_quit_releases_phone.py`; the real-mount check is in `DESIGN.md`.

## 6. Data and privacy
- [x] Settings and stats location documented, plus how to reset them (`README.md`, "Where data is kept": playlists, stats, settings, log, `.json.bak` copies, `XDG_*` overrides, and reset steps; paths checked against `__main__.py` and `logsetup.py`)
- [x] No network calls except KDE Connect on your own network (checked in the code). `rhythm_linux/` has no socket, urllib, requests, http, ssl or Soup code, and nothing calls `Gtk.show_uri`, `Gio.AppInfo` launch or `webbrowser`. The only external programs are `kdeconnect-cli` (KDE Connect, on the local network) and `idevice_id`, `ideviceinfo`, `ifuse`, `fusermount` (USB or local). Every GStreamer URI is built with `Gst.filename_to_uri` (`player.py`: lines 173 and 192, the gapless `_next_uri` and the current track), so playbin only opens local files.
- [x] Clean-room rule kept: no Apple artwork, icons or strings in the repository (`git grep` for Apple/iTunes finds only the rules and "not affiliated" notices; icons are generic `*-symbolic` and `audio-x-generic` names). Apple binaries: none inspected by this project, as far as the record shows; the rule is in `DESIGN.md`.

## 7. Accessibility and polish
- [~] **open** Keyboard-only use of every control (tab order, focus visible). Checked by simulating Tab in the running window with five tracks in the library: Tab reaches the search box, the filter and sort drop-downs, the track rows, the action buttons, play, previous, next, stop, mute, volume, shuffle, repeat, the folder button, the equaliser and crossfade drop-downs, and the sidebar. Each visible track row is a Tab stop, so Tab moves row by row through the list (arrow keys also move within it). Nothing in the code hides the focus ring; GTK's default ring is used. Pressing Space on a focused footer button used to play or pause the track instead of pressing that button (Stop paused it; Mute did nothing). Fixed: Space is left to a focused button, drop-down or check button, and still toggles play when no control has focus. Real key events in Xvfb now stop on Space at Stop and toggle Mute on Space at Mute; Enter already worked. Regression test: `tests/test_keyboard_space.py`. Light theme checked: under Xvfb (`GDK_BACKEND=x11 GSK_RENDERER=cairo`) the app was started and Tab was sent with `xdotool` (real key events, no `set_focus_visible` call), with a screenshot after each Tab. A blue ring showed on every footer control in turn (Import playlist, rating, export, send to phone, previous, play, next, stop, mute, volume, shuffle, repeat), and on the sidebar rows. The earlier "no ring" result came from a harness that did not send real keys. Dark theme checked too, on the real desktop (Hyprland 0.57.1, system colour scheme `prefer-dark`, no forced theme): Tab was sent with `wlrctl` and the window captured with `grim`. The ring appears on the same footer controls and is a clear light blue. Measured on the focused play button: ring `#5C84B9` against the footer `#222226` is 4.1:1, and against the button fill `#38383C` is 3.0:1, which meets the 3:1 non-text target in WCAG 1.4.11. The earlier Xvfb dark run used `GTK_THEME=Adwaita:dark` and showed a dimmer ring, so the Xvfb result is not the one to rely on. The item is still marked open; ticking it is left to the release owner. Side finding: Tab onto the sidebar's iPhone row switches the view and empties the track list.
- [~] **open** Screen reader labels on the icon-only buttons. Every icon-only button, the volume and position sliders, the album art and the unlabelled drop-downs and search entry now have an accessible name (`_named()` in `ui.py`: play or pause, previous, next, stop, mute, volume, shuffle, repeat, move up and down, album art, playback position, search, sort, filter, rating, equalizer, crossfade). The window builds and all 130 tests pass. Not yet checked with a screen reader: the AT-SPI registry did not start on a private session bus here, so the names could not be read back. Tried again: `/usr/lib/at-spi-bus-launcher` and `/usr/lib/at-spi2-registryd` started by hand in a private session give a working registry, but the app's window never appears in the AT-SPI desktop tree (only the portal does). GTK 4.24's Python API has no getter for an accessible label, so the names cannot be read in-process either. Read on the real Hyprland desktop (AT-SPI registry running in the session): the app appears in the accessibility tree. Buttons, the search box, sliders, sidebar rows and album art expose their names. The drop-downs did not: `Gtk.DropDown` exposes the selected value (for example "All tracks") and ignores the name set by `_named()`, which a small probe confirmed. They are now `Gtk.ComboBoxText` (`_choice_combo` in `ui.py`), and the read shows the names "Equalizer preset", "Crossfade between tracks", "Sort library by", "Show only tracks matching", "Playlist to add to" and "Rate the selected track". Still unnamed: the new-playlist and rename text fields (placeholder text is not exposed as a name). Still to do: read the names with Orca, and name those two fields.
- [ ] **open** Light and dark system themes both readable. Not yet checked: no hard-coded colours or CSS in `rhythm_linux/` (only the `dim-label` and `navigation-sidebar` style classes), so the theme comes from GTK. Under Xvfb here the screenshot attempts all came out dark, including a plain test window with the light preference set, so a light capture needs a different setup (GTK does not follow the preference in this session).
- [~] **open** The footer progress bar and time readout checked during long tracks. A 90 s file played in the real window: the time label stayed within about 1 s of the actual position, the slider followed it, a seek to 90% moved the position and the readout, and the end of the track reset the footer to 0:00 / 0:00. Found and fixed: the readout had no hours, so a track over an hour showed "75:00"; it now shows h:mm:ss from one hour (`_format_time` in `ui.py`, `tests/test_footer_time.py`). A generated 3,700 s WAV (8 kHz, 8-bit mono) played in the real window: the total read 1:01:40, the readout showed 0:01 at the start, and after a seek to 3,650 s it read 1:00:52 / 1:01:40 with the slider at 0.987. Not yet checked: that file played through from start to end in real time (the check seeked rather than waiting an hour).
